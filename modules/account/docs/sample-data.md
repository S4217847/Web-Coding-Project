# Representative MongoDB sample data

These records illustrate Dat's implemented Account and Wishlist collection
contracts. They are documentation, not credentials. The executable seed hashes
its clearly labelled demo passwords before any database write and resolves
references from inserted documents. MongoDB never receives a plaintext password,
and source data contains no usable password-reset token.

MongoDB Extended JSON is used below so ObjectIds and dates remain unambiguous.
IDs are fixed only to make the relationships easy to audit in this document.

## `users`

```json
{
  "_id": { "$oid": "66aa00000000000000000001" },
  "username": "dat.pham",
  "studentId": "S4221230",
  "name": "Dat Pham",
  "email": "s4221230@rmit.edu.vn",
  "passwordHash": "<valid bcrypt hash generated by the seed>",
  "description": "RMIT Connect administrator and student community organiser.",
  "avatarUrl": "/images/user_icon.png",
  "course": "Bachelor of Business",
  "role": "admin",
  "status": "active",
  "authVersion": 0,
  "lastActiveAt": { "$date": "2026-09-01T08:30:00.000Z" },
  "lockedAt": null,
  "deactivatedAt": null,
  "createdAt": { "$date": "2026-08-02T02:00:00.000Z" },
  "updatedAt": { "$date": "2026-09-01T08:30:00.000Z" }
}
```

The complete seed also contains an ordinary active member, a locked member,
and a deactivated member so administration filters and access-control paths
have meaningful data.

## `wishlistentries`

Saved example:

```json
{
  "_id": { "$oid": "66cc00000000000000000001" },
  "userId": { "$oid": "66aa00000000000000000001" },
  "productId": { "$oid": "66bb00000000000000000001" },
  "status": "saved",
  "quantity": 1,
  "createdAt": { "$date": "2026-09-01T08:35:00.000Z" },
  "updatedAt": { "$date": "2026-09-01T08:35:00.000Z" }
}
```

A different product can demonstrate the cart-ready state:

```json
{
  "_id": { "$oid": "66cc00000000000000000002" },
  "userId": { "$oid": "66aa00000000000000000001" },
  "productId": { "$oid": "66bb00000000000000000002" },
  "status": "cart",
  "quantity": 1,
  "createdAt": { "$date": "2026-08-29T07:00:00.000Z" },
  "updatedAt": { "$date": "2026-09-01T08:40:00.000Z" }
}
```

No seed contains two entries with the same `userId` and `productId`; the unique
compound index would reject that invalid state.

Another record may use the same User and Product to prove that favourites can
be purchased again. The snapshot name/price stay unchanged even if the current
Product is later edited.

## `passwordresettokens`

Default development seed data should not contain an active reset credential.
Reset integration tests insert a temporary record of this shape, using a real
random token hash and a test-controlled expiry:

```json
{
  "_id": { "$oid": "66ee00000000000000000001" },
  "userId": { "$oid": "66aa00000000000000000001" },
  "tokenHash": "<64 lowercase hexadecimal SHA-256 characters>",
  "expiresAt": { "$date": "2026-09-01T09:30:00.000Z" },
  "usedAt": null,
  "createdAt": { "$date": "2026-09-01T08:30:00.000Z" }
}
```

The raw reset token is never part of this document, the database record, logs,
or an API response after the one reset link is issued.

## Seed verification checklist

- Every `userId` resolves to an existing User.
- Every `productId` resolves to an existing Product.
- There is at least one `saved` and one `cart` Wishlist entry.
- There are at least two Purchase records covering more than one product; the
  schema and tests also permit a repeat purchase of the same user-product pair.
- Users cover `admin` and `member` roles plus relevant account statuses.
- Products cover search, category, name, price, and active-state queries.
- The seed is idempotent: rerunning it does not create duplicate users,
  products, or current user-product relations.
- Reset-token behaviour is generated in tests, not shipped as a usable secret.
